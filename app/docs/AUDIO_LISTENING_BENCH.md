# Audio listening bench

The bench compares actual audio files at matched playback loudness and collects blind preferences. It is the first implementation step from the [audio technology review](./AUDIO_ENGINE_REVIEW.md). It does not choose a separation vendor or prove that automatic mashups are ready for release.

The included phone demo uses a newly synthesized original loop. One version changes speed and pitch together; the other changes tempo independently. Both are prepared at the same loudness. The model labels and original filenames are withheld from the listening page. This demonstrates the comparison workflow and an audible processing difference, not real-song stem quality.

## Running a comparison

Install FFmpeg and ffprobe separately and make them available on PATH. To select specific executables, set `AUDIO_BENCH_FFMPEG` and `AUDIO_BENCH_FFPROBE`. Demo generation also requires FFmpeg's `rubberband` filter. No executable or model is downloaded by this tool, and it makes no provider calls.

From `app/`, run:

```sh
npm run benchmark:listening -- --demo
npm run benchmark:listening -- --manifest .audio-bench/comparison.json
```

The manifest supplies local paths, processing labels for the operator, and excerpts to compare:

```json
{
  "version": 1,
  "title": "Vocal clarity comparison",
  "description": "Listen to the same phrase in each version and choose which you would keep.",
  "targetLufs": -20,
  "peakCeilingDbtp": -1,
  "cases": [
    {
      "id": "pair-01-vocals",
      "title": "First chorus",
      "prompt": "Listen for vocal clarity and unwanted instruments.",
      "durationSeconds": 20,
      "variants": [
        { "id": "baseline", "method": "Exact model, weights version and settings", "path": "inputs/baseline.wav", "startSeconds": 30 },
        { "id": "candidate", "method": "Exact candidate model and settings", "path": "inputs/candidate.wav", "startSeconds": 30 }
      ]
    }
  ]
}
```

Paths resolve relative to the manifest. Use two to four variants per case and excerpts from three to ninety seconds. The operator must select the same musical material and align it before comparison. The tool checks duration and file validity; it cannot establish that two different files contain the same musical phrase.

For a useful next trial, obtain authorized source files plus a producer-made reference. Hold arrangement and edit points constant while comparing separation or time/pitch processing. Then hold the stems constant while comparing arrangements. Record model versions in `method`; include rejects and difficult examples instead of reporting only successful pairings.

## Output and privacy

Each run creates a new private directory under `.audio-bench/`, which Git ignores. `--out` can select a different new directory. Existing destinations are refused, and the runner refuses output inside the app's public/source directories. Custom output locations must be kept private and excluded from version control separately.

- `operator.json` contains the label key, source paths and hashes, processing descriptions, original clip measurements, playback measurements, gain changes, and FFmpeg version.
- `working/` contains prepared clips. These are private intermediates.
- `bundle/index.html` and `bundle/audio/` are the listener-facing files. Audio filenames are random identifiers and source metadata is removed.
- A failed run has no released `bundle/`. Its `FAILED.txt` explains that unfinished files must not be served. Retry into a new directory.

Only share the `bundle/` folder, using hosting approved for the source recordings and intended listeners. Removing labels does not make private or copyrighted audio public material. Never serve the entire run directory. The command itself uploads nothing. The committed demo contains only the original fixture generated by `scripts/audio-bench/fixtures.ts`; no existing `mp3/` audio is included.

## Measurements and matching

Inputs are hashed and read without modification. The chosen excerpts are decoded into stereo, 44.1 kHz, 24-bit PCM WAV copies. Expanding a compressed input into WAV does not restore missing information. Measurements describe these prepared excerpts; the source file's original sample rate and channels are retained in the operator report.

FFmpeg's loudnorm input fields provide integrated loudness, loudness range, and oversampled true peak. The bench uses the measured `input_*` fields rather than the filter's predicted output. Silent or unmeasurable audio is rejected.

The requested listening target defaults to -20 LUFS. A single target is chosen for all candidates in a case, lowered when needed to keep every candidate below the peak ceiling with a small margin. Each candidate receives constant gain only. No compressor, limiter, or dynamic normalization is applied for matching, because those operations could change the quality being compared.

Outputs are measured again. A mismatch exceeding 0.25 LU or a peak exceeding the configured ceiling by more than 0.05 dB prevents release of the listener bundle. These tolerances verify preparation, not musical quality. The default comparison level is not a prescribed mastering target for published songs.

## Listening and responses

Press Play A or Play B. Switching keeps the approximate playback position and uses one player per case; starting another case pauses the previous one. Listen to three seconds of each sample to unlock a preference (80% of the duration for excerpts shorter than 3.75 seconds). Choose a sample, About equal, or Neither, and optionally add notes.

Choices and listener role are stored in this browser. Reloading restores saved responses. When storage is blocked, the screen says to download results before leaving. The JSON download includes the bundle ID, case ID, selected sample ID, notes, role, and recorded playback seconds. The operator can join sample IDs to `operator.json` later.

No response is sent to a server. This is a small evaluation tool, not identity verification or fraud-resistant voting. Browser storage and downloaded responses are editable. Sample assignments are randomized once per generated bundle; regenerate assignments across panel groups when counterbalancing order matters. The bench is a blind preference comparison, not an ABX discrimination test.

## Checks and current limits

Automated tests exercise real FFmpeg output, source preservation, loudness matching, private label separation, source/path validation, silent-input rejection, and refusal to overwrite an existing run. A known 440 Hz signal verifies that speed-only processing shifts pitch while independent tempo processing retains it. Audio integration tests explicitly skip when FFmpeg/ffprobe or the required Rubber Band filter are unavailable; a skip is not evidence of audio correctness.

Browser checks cover playback, sample switching, preference gating, save/restore, JSON download, missing audio, and blocked storage on desktop Chromium and a Pixel 7 viewport. Automated choices are test data, not listener ratings. The tool still needs an actual fan/producer panel and real-song comparisons before any engine is declared better.

The existing `benchmark:audio` command remains available for its 72 metadata/arrangement checks. Its report and the lab now identify those scores as rule checks and link to the separate listening bench. Other creation flows still need the audio-engine work documented in the review.
